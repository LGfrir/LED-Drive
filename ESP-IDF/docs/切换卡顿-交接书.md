## 0. 一句话背景

ESP32-S3 驱动 4 路灯带（WS2812），手机 App 通过 BLE 控制。用户在 App 上切换某个 IO 的「手动 / 定时」模式时，**App 界面立刻显示切换成功（乐观更新），但灯带要过几秒才真正变化**，延迟不稳定（实测 0 s / 5 s / 8 s）。

## 2. 必须先理解的硬件事实（这些已用源码/日志坐实，不要再推翻）

### 2.1 ESP32-S3 只有 1 个 RMT 通道支持 DMA

`esp_driver_rmt/src/rmt_tx.c:124-128`：

```c
if (config->flags.with_dma) {
    mem_block_num = 1;
    // Only the last channel has the DMA capability
    channel_scan_start = RMT_TX_CHANNEL_OFFSET_IN_GROUP + RMT_LL_GET(TX_CANDIDATES_PER_INST) - 1;
}
```

**结论：4 路灯带里只能有 1 路走 DMA，其余 3 路必然是 48 符号中断补数。**
启动日志里那三条 `rmt_tx_register_to_group: no free tx channels` 是**必然结果，不是故障**。不要试图"修好它"，也不要让 4 路都申请 DMA。

### 2.2 DMA 块大小硬上限 2047 个符号

`rmt_tx.c:77-82`：

```c
mount_size_per_node = ALIGN_DOWN(mem_block_symbols * 4 / 2, 4);
ESP_RETURN_ON_FALSE(mount_size_per_node <= DMA_DESCRIPTOR_BUFFER_MAX_SIZE, ...,
                    "mem_block_symbols can't exceed %zu",
                    DMA_DESCRIPTOR_BUFFER_MAX_SIZE * RMT_DMA_NODES_PING_PONG / sizeof(rmt_symbol_word_t));
```

`4095 × 2 ÷ 4 = 2047`；且 `rmt_tx.c:262` 要求 `mem_block_symbols` **必须是偶数且 ≥48**。
⇒ **合法最大值是 2046。** 2048 会因节点 4096 > 4095 被拒。

### 2.3 两种补数模式的代价

| 模式 | 一块的发送时间 = 补数截止期 | 500 颗灯每帧补数次数 |
|---|---|---|
| 48 符号（无 DMA） | **60 µs** | **250 次**（必花屏） |
| 2046 符号（DMA） | **1.28 ms**（乒乓节点 1023 符号） | 12 次 |

WS2812：1.25 µs/位，24 位/颗 → **30 µs/颗**。数据断流几十 µs 就会整条错位。

### 2.4 Flash 写会冻结系统

ESP32 代码从 Flash 执行（XIP）。`nvs_commit` 期间关闭 code cache：当前核的 IRAM 中断仍可运行，**另一个核被整体冻结**。
因此 `light_persist_task` **必须钉在 core 0**（与 RMT 中断同核）。

### 2.5 NVS 是追加日志，不能改成原地覆盖

NOR Flash 只能按 4 KB 扇区擦除（20–40 ms）。"原地写几个字节"在硬件上不存在。正确做法是**减少写入次数 + 批量一次 commit**，不是取消追加。

### 2.6 FreeRTOS tick = 100 Hz

`CONFIG_FREERTOS_HZ=100` ⇒ `pdMS_TO_TICKS(5..9) == 0`，而 `vTaskDelay(0)` 是"立刻回来"不是"睡 0 ms"。任何 <10 ms 的延时都会退化成空转。

|---|---|---|---|---|
| 1 | 14 | 96 | 3 | |
| 2 | 4 | 500 | 15 | 压测配置，**唯一拿到 DMA 的** |
| 3 | 5 | 60 | 2 | |

## 5. 已排除 / 已确认的假说

| 假说 | 结论 |
|---|---|
| RMT 通道数不够/配置错 | **排除**。S3 只有 1 个 DMA 通道，3 路非 DMA 是硬限制 |
| `mem_block_symbols` 超 2047 | **已修**。夹到 2046 |
| 非 DMA 导致 500 颗必花屏 | **已修**。500 颗走 DMA，每帧 12 次补数 |
| 固件落盘静默期把灯拖住 | **已修**。节拍与落盘拆开，最坏 100 ms |
| `vTaskDelay(0)` 空转饿死 BLE | **已修**。`vTaskDelayUntil` + 最小 1 tick + 非 DMA 下限 |
| App 有 5 s 常量在节流 | **排除**。App 内只有 `withTimeout(5_000)`（读写回调超时）与 `takeResult` 的 `8_000`，没有节流常量 |
| **GATT 回调在主线程、被动画堵住** | **高度可疑，刚改完待验证**。`write()/read()` 等回调有 5 s 超时，超时期间持有 `gate` 互斥，下一条命令排队 ⇒ 延迟呈 5 s 的倍数 |

**当前主假说**：主线程被预览动画占满 → `onCharacteristicWrite`/`onCharacteristicRead` 回调排队 → 5 s 超时 → `gate` 被占用 → 后续命令再等 5 s。这能解释 0 / 5 / 8 s 的不规则分布。

### 6.2 切一次模式，读数

串口应出现：

```
I (xxxxx) gatt_time: io_mode 写入 io=1 mode=1 t=123456ms
```

| 观测 | 判定 | 下一步 |

### 6.3 若判定为固件应用慢

重点看 `main/src/task/clock_scheduler.c` 的 `run_once_locked()`：

1. `b->editing == true` 会让整段被跳过。检查 `clock_seg_local_write()` 是否把 `editing` 置上后没被清（`edit_cmt save=0` 没发出去）。
2. `local_clock_valid() == false` 时时间模式会 `light_io_set_mute(io, true)`（**灯灭**）。确认设备已完成对时——`bootstrapClock()` 失败时 `_clockReady=false`，App 侧 `setIoMode` 会拦住并提示"定时暂时不可用"。
3. `light_io_recall_manual()`（定时→手动）逐段恢复，若 `held_valid == false` 会逐段读 NVS（IO2 有 15 段）。可加计时日志确认。
4. 确认 `clock_io_mode_set()` 的幂等早退没有误命中（`prev == mode` 时不置脏、不重置 `applied`，靠 100 ms 节拍兜底）。

建议在这三处加 `esp_timer_get_time()` 打点，定位到具体函数。

### 6.4 若判定为 App 侧排队

1. 抓日志：
   ```powershell
   & "E:\IDE\Android SDK\platform-tools\adb.exe" logcat -v time -s LEDDriveBT
   ```
   App 自带 `commLog`（`note("手机→灯带", ...)`），带时间戳。
2. 看 `ble/LightBleClient.kt` 的 `gate`（`Mutex`）被谁长时间占住：
   - `write()` / `read()` 各 `withTimeout(5_000)`
   - `readPreset()` 最多 8 个分块
   - `loadSegment()` 一次锁内做约 8 次读
   - `loadPresets()` 逐条读 32 条预设（每条 ≥2 块）
   - `ensureMonitor()` 逐段读全部灯段
3. 关键怀疑点：`setClockIoMode` 末尾的 `reloadClockStatLocked()` 仍在 `gate` 内；若该读回调丢失，会把锁占满 5 s，**下一次切换再等 5 s**。可改为锁外 best-effort，或干脆去掉（`nextEvent` 与 IO 模式无关，见下）。

> 附：`clk_stat` 里 App 实际只用到 `nextEvent`；而 `clock_next_event_sec()` 只扫调度表，**与 io_mode 无关**。所以"切模式后重读 clk_stat"这一步在语义上可以省略。

## 8. 约束（改代码前必读）

1. **不要**把 `mem_block_symbols` 改回"按整帧大小申请"（>2047 必失败，退回 48 符号反而更糟）。
2. **不要**让 4 路都申请 DMA——硬件只有一个 DMA 通道。按灯珠数降序创建这条规则要保留。
3. **不要**把调度节拍与 NVS 落盘静默期合并成一个常量（这就是 5 s 卡顿的直接原因）。
4. **不要**恢复灯带页每段 60fps 预览（用户明确要求删除，且它是主线程堵塞源）。
5. **不要**把 NVS 改成"固定布局原地写"——NOR Flash 只能整扇区擦除，会更慢。
6. `light_persist_task` **必须** `xTaskCreatePinnedToCore(..., 0)`（与 RMT 中断同核）。
7. 协议以 `docs/APP_TASKS.md`（v0.2 冻结）为准，不要修改包格式。
8. 固件 `main.c` 的 IO 配置（96/500/60/30 颗）是压测配置，改动前先与产品确认。

## 10. 交接时的已知风险

- 固件最后一轮（100 ms 节拍 + 日志埋点）**未烧录**，接手后必须先烧。
- 用户对"删掉每段预览"是明确同意的；若想恢复视觉反馈，应改用**静态色块**（不跑帧循环）。
- NVS 分区只有 64 KB（`partitions.csv`），芯片实际 16 MB 只声明了 2 MB。扩分区会清空 NVS，需先让用户导出备份。
- 未做：`requestConnectionPriority(CONNECTION_PRIORITY_HIGH)`。加上可把每次往返从 30–50 ms 压到 11–15 ms，是低风险收益项。
- 未做：`clk_stat` 读取在 BLE 回调里按灯段逐个加锁（`clock_seg_active_preset` 每次 `xSemaphoreTake`），可改一次加锁拷快照。
